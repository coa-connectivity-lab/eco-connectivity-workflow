# Contributing

This project is built collaboratively, with a lot of the code generated by Claude
and then reviewed by the team. The workflow below is deliberately close to how the
Linux kernel and most large open projects work: the mainline only ever moves
forward through reviewed changes, provenance is kept clean, and every change
records what a human actually checked.

Read [`GOVERNANCE.md`](GOVERNANCE.md) for who the maintainers and module owners
are, and [`docs/onboarding.md`](docs/onboarding.md) for local setup and a
step-by-step first change.

## 1. Ground rule

`main` is protected. Nobody commits or pushes to it, including maintainers. Every
change lands through a branch and a reviewed pull request. If you have push access,
that access is for pushing branches, not `main`.

## 2. One change per branch

- Branch off the latest `main`.
- Name branches `area/short-description`, where `area` is one of `data`, `db`,
  `ml`, `qgis`, `logs`, `docs` (matching the modules in
  [`GOVERNANCE.md`](GOVERNANCE.md)). For example `data/add-elevation-source` or
  `ml/resistance-transform-c-param`.
- One logical change per branch. Keep it small enough that a reviewer can hold the
  whole thing in their head in one sitting.

## 3. Keep history linear

Rebase your branch onto the latest `main` before you open the pull request and
again before it merges. Do not merge `main` into your branch. `main` requires a
linear history, so a branch with merge commits cannot be merged.

```bash
git switch main && git pull --ff-only
git switch your-branch && git rebase main
```

## 4. Commit messages

- Subject line in the imperative mood, 50 characters or fewer: "Add SRTM elevation
  acquisition step", not "Added..." or "Adds...".
- Blank line, then a body wrapped at 72 characters explaining **why** the change is
  needed, not just what it does.
- Reference issues with `Refs #123` or `Closes #123` on their own line.

## 5. Sign your work (DCO)

Every commit carries a `Signed-off-by:` trailer, added automatically with:

```bash
git commit -s
```

By signing off you assert the
[Developer Certificate of Origin](https://developercertificate.org/): you wrote the
change, or you have the right to submit it under this project's licence. This is
the same mechanism the kernel uses and it keeps the provenance of the codebase
clean.

## 6. Disclose AI assistance

Much of this codebase is generated with Claude, so every pull request fills in the
**AI assistance** block of the template:

- (i) which files or functions were AI-generated or AI-edited;
- (ii) the prompt or approach, in one or two plain sentences, or a link to the
  transcript where the prompt itself determined the result;
- (iii) what you, the human author, verified, and how: ran the pipeline end to end,
  compared an output raster against a known-good one, checked CRS and grid
  alignment, read every line, and so on.

This follows the disclosure-threshold and placement thinking behind the WCRI/GFRN
global AI-disclosure standard: disclose AI use that substantively shapes a result,
put the disclosure where a reviewer will actually read it, and record human
verification rather than implying the tool carries responsibility for the result.

Routine editor autocompletion does not need disclosing. AI use that shaped a
method, a parameter choice, a data-cleaning decision, or a non-trivial block of
code does.

## 7. Review before merge

- At least one maintainer approves before a pull request merges.
- `CODEOWNERS` automatically requests the owner of any module the change touches.
- Reviewers check correctness, that the data-handling rules in section 9 are
  respected, and that the AI-assistance block is filled in honestly.

## 8. Merge style

"Rebase and merge" only. Squash-merging would collapse the branch into one commit
and drop the per-commit `Signed-off-by` trailers, so it is disabled.

## 9. Reproducibility gates

A pull request has to clear these before it merges:

- (i) no data files added to Git. New data comes with an `acquire_*` script and a
  cited, licensed source. Raw downloads are cached and referenced by their DOI.
- (ii) sensitive-species locations (currently the European wildcat) are generalised
  to a 5 km grid cell before they reach any figure, map, or export.
- (iii) dependencies stay pinned in `environment.yml`. A new package is justified in
  the pull request description.
- (iv) any change to the analysis is runnable end to end from the single entry
  script, not just from a notebook cell.
- (v) a run that changes outputs adds an entry to the `reproducibility-logs`
  repository.

## 10. State limitations in the code

Docstrings and notebook prose name the method's weak points plainly. Do not quietly
smooth over a thin occurrence sample, an in-sample accuracy figure presented as if
it were validation, or a resampling step that dilutes fine-scale evidence. This is
already the house style of the baseline study. Keep it.

## 11. FAIR for research software

- Keep `CITATION.cff` and `codemeta.json` current when authorship or dependencies
  change.
- Tag releases with semantic versions (`v0.2.0`).
- Tagged releases are archived to Zenodo and Software Heritage and cited by their
  SWHID, the same way a dataset is cited by its DOI.

## 12. Local setup

See [`docs/onboarding.md`](docs/onboarding.md) for the environment, a local PostGIS
instance, and a worked first pull request.
