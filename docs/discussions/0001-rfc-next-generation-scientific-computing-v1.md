# RFC: measuring this pipeline against the 2025 next-generation scientific computing report

## Why this thread

The report of the *2025 Workshop on Next-Generation Ecosystems for Scientific
Computing* is out: [*Reimagining Scientific Computing in the Age of AI*](https://arxiv.org/abs/2510.03413)
(arXiv:2510.03413, [full PDF](https://arxiv.org/pdf/2510.03413)). It gathers more
than 40 people from national laboratories, academia, and industry around one idea,
**socio-technical co-design**: the social and technical parts of a scientific
software ecosystem should be designed together, not bolted on to each other later.
Its three headline recommendations are (i) build modular, trustworthy AI-enabled
software; (ii) let teams bring AI into their workflows while keeping human
creativity, trust, and rigour; (iii) build training pipelines that keep pace with
the technology. Its near-term priorities are hybrid AI/HPC infrastructure,
cross-disciplinary collaboration and pedagogy, responsible-AI guidelines, and
prototyping public-private partnerships.

That report is written for large facilities. This project is the opposite end of
the scale: a laptop-only, pure-Python pipeline for rewilding and restoration teams
that cannot take on a heavy software stack. It is also already built the way the
report describes, code generated by Claude and reviewed by the team, with an
AI-disclosure convention and reproducibility gates in [`CONTRIBUTING.md`](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/CONTRIBUTING.md).
So it is a fair small-scale test: do the report's recommendations survive contact
with a project that has almost no infrastructure to spend on them?

This is an RFC, not an essay. Each item below ends in a concrete step and an open
question. Agreed items become tracked issues. This post was itself drafted with
Claude and reviewed before posting, the same [`CONTRIBUTING.md`](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/CONTRIBUTING.md)
section 6 convention we apply to code, applied to prose.

## Where we think we already align

- (i) The five-module split in the [README](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/README.md) is a modular design, even
  though the module repositories are still empty.
- (ii) `main` is protected on every repository, rebase-only history, one maintainer
  approval plus a `CODEOWNERS` review before merge ([`CONTRIBUTING.md`](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/CONTRIBUTING.md)
  sections 1, 3, 7, 8).
- (iii) Every pull request fills in an AI-assistance block: which files, what prompt
  or approach, and what a human verified and how ([`CONTRIBUTING.md`](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/CONTRIBUTING.md)
  section 6), following the WCRI/GFRN disclosure standard.
- (iv) Reproducibility gates: no data in Git, sensitive-species generalisation,
  pinned dependencies, one entry script, a provenance log entry when outputs change
  ([`CONTRIBUTING.md`](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/CONTRIBUTING.md) section 9).
- (v) FAIR items: `CITATION.cff` and `codemeta.json` kept current, tagged releases
  archived to Zenodo and Software Heritage and cited by SWHID ([`CONTRIBUTING.md`](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/CONTRIBUTING.md)
  section 11).
- (vi) Governance is deliberately light: lazy consensus, module owners, one named
  data steward ([`GOVERNANCE.md`](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/GOVERNANCE.md)).

## Proposed roadmap

| Report recommendation or priority | Proposed step here | Open question |
| --- | --- | --- |
| Modular, trustworthy AI-enabled software | Define an interface contract per module repository; add a cross-module test that runs the `demo.ipynb` chain end to end in CI (today `ci.yml` only runs on pull requests to this repo); pin a per-module `environment.yml` | Are the module boundaries in the README table the right cut, while the repositories are still empty and cheap to change? |
| Trust rests on provenance | Specify the `reproducibility-logs` schema: inputs and their DOIs, environment hash, git SHA, output checksums, and the SWHID or DOI of the release that produced them | What is the smallest provenance record a resource-limited partner team can realistically keep every run? |
| Bring in AI, keep rigour | Make part of the pull-request AI-disclosure block machine-readable (a parsed field, or an entry in `codemeta.json`); adopt a transcript-archiving convention; write a short fixed vocabulary for "what a human checked" (ran end to end, compared a raster against known-good, checked CRS and grid alignment, read every line) | Is the free-text block enough, or does it need structure to stay auditable a year from now? |
| Responsible-AI guidelines | Turn the report's guideline call into a one-page project AI policy in `docs/`, anchored to the WCRI/GFRN standard already cited in `CONTRIBUTING.md` | What is in scope beyond code generation: parameter choices, data-cleaning decisions, figure text? |
| Cross-disciplinary collaboration and pedagogy | Promote [`docs/onboarding.md`](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/docs/onboarding.md) into a teachable worked example: an ecologist and RSE pairing model, a guided path through the baseline study, a visible contribution ladder | How do we onboard an ecologist who does not use Git without weakening the reproducibility gates? |
| Training pipelines that keep pace | A short, versioned "how we work with AI here" document, expected to change often, with its own changelog | Who owns keeping it current as the tools change? |
| Hybrid AI/HPC infrastructure | State the scaling boundary in writing: the landscape size and resolution at which a partner exceeds laptop scale, and the fallback (Planetary Computer compute, tiled runs) that keeps the "no paid services, no cluster" promise for the default path | Where is that boundary on a 100 m grid, and what breaks first: memory, the `scipy.sparse` solver, or raster I/O? |
| Prototyping public-private partnerships | Document the partnership pattern already in use, Rewilding Portugal plus Microsoft Planetary Computer plus Zenodo and Software Heritage, as a template other restoration teams can copy | Which parts of that pattern are portable, and which are specific to the Côa programme? |
| Socio-technical co-design (the framing) | Check whether [`GOVERNANCE.md`](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/GOVERNANCE.md) scales when an outside team *adopts* the pipeline for its own landscape rather than contributing code to ours | Do adopters need a lighter role than "contributor", and what would it grant? |

## How to take part

Comment on the rows that matter to you. Where a row reaches lazy consensus, two
working days with no substantive objection, I will open an issue for it under the
relevant module. Anything that adds a dependency, changes the method, or changes a
schema gets its own issue first, per [`GOVERNANCE.md`](https://github.com/coa-connectivity-lab/eco-connectivity-workflow/blob/main/GOVERNANCE.md). If you run
a rewilding or restoration project that cannot take on a heavy stack, the scaling
and adoption rows are the ones I most want your read on. Which of these is worth
doing first, and is any of it solving a problem we do not have?
